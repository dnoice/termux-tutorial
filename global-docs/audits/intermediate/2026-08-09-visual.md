Every hex, px and ratio below was read off a live render at `http://localhost:4322/termux-tutorial-intermediate/`, not inferred from source. Source was consulted only to name a cause after the symptom had already been measured.

## Executive summary

The chrome of this course is in excellent shape, and the reason is that it inherited a finished stylesheet: `src/styles/global.css` is byte-identical to the beginner course's apart from one re-added Starlight card block, so every fix from the 2026-08-06 audit is already in place here. It shows. There is **zero page-level horizontal overflow** at 390, 768 or 1440 on any page. There is **not one text element below WCAG AA** on any of the six pages in either theme — 50 text-bearing elements on the landing page alone, all passing, in both Obsidian and Parchment. Lists and paragraphs share one face and one size (Source Serif 4, 17px). Every heading is Crimson Pro. Card and panel grids reflow 1 -> 2 -> 3/4 columns with equal heights inside every row. The theme toggle is reachable at 390px on both page types. The typographic and colour work simply arrived pre-done.

What is broken is everything this course added on top, and it is broken badly. **Not a single React island renders on any page.** Every one of them — `ProfileBadge`, `LessonComplete`, `LiveSandbox` — ships as an empty `<astro-island>` of zero height, throwing `TypeError: _jsxDEV is not a function` into the console on every page load. The consequence is not subtle: there is no "Mark complete" button on any of the seven lessons, so `/progress/` can never be filled and renders as a title, one paragraph, one aside and then nothing; the sidebar profile slot is a blank reserved box; and the h2 "Practise the mechanics in a real Linux box" on the scripting lesson is followed by empty space where the Debian VM should be. The beginner dev server, running on the same machine at the same minute with identical dependencies, hydrates the same components fine — 703, 1,060 and 60,509 characters of DOM against this course's 0, 0 and 0.

Underneath that sits a second, independent problem: the course *describes* interactive terminals that were never built. The landing page devotes an h2 and two panels to "The Practice Terminal — the fish-style shell up the page" and "The Live Sandbox — it appears in the scripting lesson", the "Before you start" aside says "The practice terminal above is still here for muscle memory", and the sidebar badges the scripting lesson **Interactive**. There is no terminal markup anywhere in the course. The landing page contains exactly one island and it is the profile badge.

Then the phone problem this course creates for itself. This is a course about long paths, long crontab lines and long tunnel invocations, rendered in a 358px column. **75 of 155 code blocks — 48% — scroll horizontally at 390px.** The worst is the crontab line on `automation/scheduling/`: 1,013px of content in a 357px box, 65% of it off-screen, and it is a line the learner must reproduce character-for-character. Sitting on top of that content, permanently, is Expressive Code's 32 x 32 copy button at 0.55 opacity, covering roughly four monospace characters at the right edge of every single block. And two of the four pages linked as the course's reference material — the cheatsheet and troubleshooting — are one-sentence stubs that render as a heading, a promise, and 450px of empty background.

Nothing here is a design failure. The design is fine. This is a course that was assembled but never run.

> one: it noted that `_jsxDEV` is a dev-runtime symbol and that it had not
> checked a production build. It had not, because the brief forbade running one.
> That check has now been done, and the finding does not survive it.
>

> 20 buttons present. The built HTML carries real hashed chunks

> Vite's dev transform, so an error naming it can only ever be a dev-server

> Cause: a stale Vite dependency-optimizer cache in the long-running dev server

**Original finding, retained for the record:**

**Severity:** ~~Critical~~ → withdrawn · **Effort:** Medium · **Pages:** all 12 routes · **Spans:** all three viewports, both themes

**Observed.** On `bridge/api-setup/` at 390px, `document.querySelectorAll('astro-island')` returns two elements. Both have `innerHTML.length === 0` and a bounding box of `0 x 0`:

```text
{ u: "ProfileBadge.tsx",    len: 0, h: 0 }
{ u: "LessonComplete.tsx",  len: 0, h: 0 }
```

The console carries a matching exception per island, on a direct tab navigation (no iframe, no theme manipulation, `crossOriginIsolated === false`, no service worker registered):

On `automation/shell-scripts/` a third island fails differently:

```text
TypeError: Failed to fetch dynamically imported module:
http://localhost:4322/src/components/terminal/LiveSandbox.tsx?astro-retry=1
```

Waiting a further four seconds after load changes nothing — all three remain at `len: 0, h: 0`.

The visible consequences, in order of how much they cost a learner:

- **No "Mark complete" control on any lesson.** `document.querySelectorAll('.tmx-lesson-complete')` returns 0 on all seven lesson pages. The progress system has no input.
- **`/progress/` is an empty page.** At 390px it renders the h1 "Your Progress", the paragraph "This is your personal dashboard. Set a display name and avatar, and check off lessons as you finish them", one note aside, "Edit page", and then roughly 150px of bare scatter field to the fold. `documentElement.scrollHeight` is exactly 844 — the page does not reach one screen. Total markdown text: 450 characters. The dashboard, the avatar, the name field and the checklist the paragraph promises are all inside the dead island.
- **The scripting lesson has a hole in it.** `automation/shell-scripts/` carries the h2 "Practise the mechanics in a real Linux box" and nothing under it. `astro.config.mjs` goes to the trouble of moving `SANDBOX_PATH` to this route and registering the COI service worker for it; the component it exists to serve never mounts.
- **The sidebar profile slot is blank.** `.tmx-profile-slot` reserves 98px (deliberately, to prevent a layout shift) and then stays empty on every page.

**Control.** The beginner course, served from `localhost:4321` on the same machine at the same minute, with byte-identical `dependencies` in `package.json` (`@astrojs/react ^6.0.1`, `react ^19.2.7`, `astro ^7.0.2`), hydrates the same components:

```text
{ u: "ProfileBadge.tsx",    len:   703 }
{ u: "TermuxTerminal.tsx",  len: 60509 }
{ u: "TermuxTerminal.tsx",  len: 60497 }
{ u: "LessonComplete.tsx",  len:  1060 }
```

So this is not a machine problem, a React-version problem or a browser problem. It is specific to this repository's install or Vite state.

**Cause.** `_jsxDEV is not a function` is the automatic JSX dev runtime failing to resolve: the module namespace React's dev transform imports (`react/jsx-dev-runtime`) is coming back without `jsxDEV`. In practice that means this repo's `node_modules/.vite/deps` pre-bundle is stale or was built against a different React resolution than the one now loaded. `Failed to fetch dynamically imported module` on `LiveSandbox.tsx` is the same optimiser failing a step earlier, on the chunk itself.

**Recommendation.** Clear `node_modules/.vite` and reinstall, then reload and confirm all three islands report non-zero `innerHTML.length`. If it survives that, check for a duplicated React in the tree (`npm ls react react-dom`) — two copies is the usual source of a missing `jsxDEV`. **Then verify against a production build**, which this audit was instructed not to run: `client:only` islands behave differently under `astro build`, and a green dev server is not proof. Add a smoke check that asserts at least one `.tmx-lesson-complete` button exists on a built lesson page, because the failure mode here is completely silent — nothing is red, nothing is missing from the layout, there is simply less page.

### M2 (original). The course advertises three terminals and an "Interactive" badge; none of them exist in the markup

**Severity:** High · **Effort:** Large · **Pages:** landing `/`, `automation/shell-scripts/`, sidebar on every page · **Spans:** all viewports, both themes

**Observed.** Across all ten content routes, `document.querySelectorAll('.xterm, .tmx-terminal, .tmx-sandbox')` returns **0**. Against that, the rendered pages say:

- The landing page's "Before you start" aside, at 390px: "**Bring a real phone this time.** The practice terminal above is still here for muscle memory, but every `termux-*` command in this course talks to actual Android hardware." There is nothing above it but a headline, a tagline, a button and two paragraphs.
- An h2, "Three places to type things", opens: "Course one had two terminals. This one has three, and knowing which is which saves you an hour of confusion." ### M3. Half of every code block runs off the side of the phone

**Severity:** High · **Effort:** Medium · **Pages:** all seven lesson pages · **Mobile (390px); still present at 768px**

**Observed.** At a 390px viewport the markdown column is 358px wide (`16px` inset each side) and a code block's scrollport is 313-357px depending on nesting. Measuring `scrollWidth` against `clientWidth` on every `<pre>`:

| Page | `<pre>` blocks | Overflowing | Worst block |
| --- | --- | --- | --- |
| `bridge/api-setup/` | 11 | 3 | 400px in 357px |
| `bridge/reading-the-device/` | 34 | 16 | 610px in 357px |
| `bridge/talking-back/` | 18 | 17 | 694px in 357px |
| `automation/shell-scripts/` | 36 | 13 | 645px in 313px |
| `automation/scheduling/` | 23 | 15 | **1,013px in 357px** |
| `serving/local-server/` | 20 | 8 | 627px in 357px |
| `serving/tunnels/` | 13 | 3 | 467px in 313px |
| **Total** | **155** | **75 (48%)** | |

The worst case, `automation/scheduling/`, is worth naming in full because of what it is. The block renders as `0 7 * * * /data/data/com.termux/files/hom` and stops; the full line is:

```text
0 7 * * * /data/data/com.termux/files/home/bin/battery-check.sh >> /data/data/com.termux/files/home/cron.log 2>&1
```

357 of 1,013 pixels are visible — **65% of the line is off-screen**, including both redirections, which are the entire point of the example. Four more blocks on that page hide 47-60%. The learner has to horizontally scroll a 22px-tall strip, inside a vertically scrolling page, to read a line they must then reproduce exactly.

An affordance does exist: the scrollport keeps a persistent horizontal scrollbar, visible in the render as a ~115px thumb in a ~335px track under the code. So the content is reachable. It is the reading experience that fails, not the mechanism.

At 768px the same blocks still overflow — 12 elements exceed the 612px column on `automation/scheduling/`, with the 1,013px line unchanged.

**Cause.** Authored content, not CSS. This course's subject matter is absolute Termux paths (`/data/data/com.termux/files/home/…`, 41 characters before anything useful), crontab lines, and multi-flag `termux-job-scheduler` invocations, and they were written at desktop width. The stylesheet is doing the right thing by scrolling rather than wrapping; there is simply far more content per line than in course one.

**Recommendation.** Fix this in the content, not the stylesheet. Three moves, in order of value: (1) use `~` and `$HOME` in prose examples and reserve the absolute path for the one place it genuinely matters — cron's missing `PATH` — where it can be split across a `PATH=` line and a short command; (2) break long invocations across lines with `\` continuations, which this course already does correctly for `termux-job-scheduler` and should do everywhere; (3) for the handful of lines that genuinely cannot be shortened, turn on Expressive Code's `wrap` meta option so they soft-wrap instead of scrolling. Then re-measure: the target is no block hiding more than about a third of its widest line at 390px.

### M4. Two of the four "Reference & Tools" pages are one-sentence stubs

**Severity:** High · **Effort:** Large · **Pages:** `reference/cheatsheet/`, `reference/troubleshooting/` · **Spans:** all viewports, both themes

**Observed.** `reference/cheatsheet/` contains **138 characters** of markdown, in one `<p>`, and **zero tables**:

> Coming up: every `termux-*` command, cron field, scheduler flag and tunnel invocation from this course, on one page you can grab in a hurry.

At 390px the whole page is: sticky header, the "On this page > Overview" bar, the h1 "Command Cheatsheet", that paragraph, "Edit page" at y=401, and then roughly 430px of bare scatter field to the bottom of the viewport. `documentElement.scrollHeight` is exactly **844** — it does not fill one phone screen, and it is the only page in the course with no vertical scrollbar at any viewport (measured `clientWidth` 405 at phone and 1455 at desktop, i.e. the full iframe width, because no scrollbar is reserved).

`reference/troubleshooting/` is worse: **99 characters**, one paragraph, same empty page.

Both are listed in the sidebar under "Reference & Tools" with no "coming soon" marker, and both are linked from running prose on `where-next/` in language that describes finished pages:

> The **Command Cheatsheet** has every `termux-*` command, cron field, scheduler flag and tunnel invocation from this course on one page.
>
> **Troubleshooting** covers the failures this course actually produces: the API command that hangs instead of erroring, a permission denied once and never asked about again, the cron job that ran for a day and then quietly stopped…

For contrast, the seven lesson pages carry 8,804 to 22,844 characters each.

**Cause.** Placeholder routes shipped into the published sidebar and cross-linked from finished prose.

**Recommendation.** Either write them or hide them. If they are days away, the cheapest honest fix is to add a `Coming soon` badge to both sidebar entries (the badge system is already in use — `Interactive`, `Careful`, `Finish`, `Local` all render correctly) and soften the `where-next/` sentences from "has every…" to "will collect…". If they are further out, drop both from the sidebar and the `where-next/` list entirely; a missing page is better than a page that renders as a promise over 430px of nothing. Note that this is the one place where a course-one convention was *not* inherited: the beginner cheatsheet is a real six-table reference, which is exactly what a learner arriving here will expect.

### M5. The copy button sits on top of the code, on all 155 blocks

**Severity:** Medium · **Effort:** Small · **Pages:** all seven lesson pages · **Mobile (390px)**

**Observed.** On `automation/scheduling/`, the 1,013px crontab block from M3 renders at `x: 16, width: 358`. Its copy button computes:

```text
position: relative, z-index: 1, opacity: 0.55
background-color: rgb(20, 24, 32)
box: 32 x 32 at x = 333  (right edge 365)
```

The code line inside runs from `x: 16.7` to `x: 1029.7`, so at `scrollLeft: 0` the button is painted over live code from 333 to 365 — the last ~32px of a 358px window. At the block's 14px JetBrains Mono, that is roughly **four characters permanently obscured**, at the right edge, which is precisely the direction the learner is scrolling. In the render the line reads `…com.termux/files[button]hom`, with the button's semi-opaque fill sitting over the glyphs rather than beside them.

At 32 x 32 the button is also below the 44px touch floor, and it is the most-used control on a page with 23 code blocks.

**Cause.** Expressive Code's stock copy button geometry, kept visible at rest on touch by the deliberate `@media (pointer: coarse)` rule in `global.css:924`. Keeping it visible on touch is right — it is unreachable by hover — but the frame reserves no gutter for it, so on a narrow column it lands on the content instead of beside it.

**Recommendation.** Give the button its own lane below 50rem rather than overlaying the code: add `padding-inline-end: 2.75rem` to the `<pre>` scrollport (or shift the button into the frame's title bar, which is already reserved space and already 37px tall). While there, take it to 44 x 44 via the existing `.tmx-tap-icon` pattern. Both are single rules and neither touches the desktop rendering, where the 720px column has room to spare.

### M6. Two tables scroll horizontally at 390px

**Severity:** Low · **Effort:** Small · **Pages:** `automation/scheduling/`, `bridge/api-setup/` · **Mobile (390px)**

**Observed.** Of the 20 tables across the seven lesson pages, two exceed their scrollport at 390px:

- `automation/scheduling/`, the fourth table (3 columns, header row empty): `clientWidth: 357`, `scrollWidth: 407` — 50px, 12% hidden.
- `bridge/api-setup/`, the first table (3 columns: Half / What it is / How you install it): `clientWidth: 357`, `scrollWidth: 364` — 7px hidden.

Both carry `overflow-x: auto` and sit on the opaque `--bg-surface` card treatment, so the scroll works and nothing collides with the background. The other 18 tables fit the column exactly. Neither table contributes to page-level overflow: `body.scrollWidth` stays at 390 on both pages.

**Cause.** Content width, not layout. In both cases a single cell's min-content width (a `pkg install termux-api` chip, a flag column) pushes the table a few dozen pixels past the column.

**Recommendation.** Low priority. The 7px case is invisible in practice. For the 50px case, either shorten the widest cell or allow `word-break` inside that column's chips. Worth confirming the scroll cue is discoverable on a real touch device before spending anything here — on desktop the scrollbar is persistent, on Android it is not.

### M7. `.sl-markdown-content` reports 7-8px of internal overflow that no child accounts for

**Severity:** Nit · **Effort:** Small · **Pages:** `where-next/`, `serving/tunnels/`, `automation/scheduling/` · **Mobile (390px)**

**Observed.** On `where-next/` at 390px the markdown column measures `clientWidth: 358, scrollWidth: 366`. On `serving/tunnels/` it is 358 / 365; on `automation/scheduling/` 358 / 363. Walking every descendant, **no element's right edge exceeds the column's right edge**, so the overflow is not attributable to a child box. On `where-next/` and `serving/tunnels/` an `.sl-heading-wrapper.level-h2` reports the same 7-8px delta, which points at the heading anchor rather than the prose.

No visible consequence: `overflow-x` on the column is `visible`, `body.scrollWidth` equals `documentElement.clientWidth` at 390 on all six pages, and there is no page-level horizontal scrollbar anywhere.

**Cause.** Not established. Most likely the absolutely-positioned `.sl-anchor-link` (measured at 24 x 35.8) or a negative-inset pseudo-element contributing to scroll width without contributing a laid-out box.

**Recommendation.** Leave it unless something else starts overflowing. Recorded only so that a future 390px overflow is not mistaken for a regression when it is this pre-existing 8px.

## Inherited from the shared stylesheet — present in the beginner course too, listed for completeness

`src/styles/global.css` in this repository differs from the beginner course's in exactly one region — the re-added Starlight `.card` / `.card-grid` / `a.card` block and its reduced-motion twin. Everything else is identical. The three items below were measured on the intermediate site but reproduce on the beginner site, so they are **not** intermediate defects and should be fixed once, upstream, for both courses.

**I1. On a phone the lesson `h1` and its `h2`s are the same size.** At 390px on `automation/scheduling/`: `h1` = Crimson Pro Variable **31px / 700 / 35.65px line-height**; the first markdown `h2` = Crimson Pro Variable **31px / 700 / 35.65px**. ## What is working, and should not be broken while fixing the above

Stated explicitly because several of these were expensive to earn in course one and are worth protecting.

- **No horizontal overflow anywhere.** `body.scrollWidth === documentElement.clientWidth` on all six pages at 390, 768 and 1440. The full-bleed and negative-inset tricks in the stylesheet all hold at phone width.
- **No AA contrast failures on any of the six pages, in either theme.** A sweep of every text-bearing element with a computed background (excluding gradient-filled buttons and `background-clip: text`, which a compositing check cannot resolve) returned **zero** results below 4.5:1 (3:1 for large text) in both Obsidian and Parchment. On the landing page that was 50 elements checked, 4 gradient-skipped, 1 clip-skipped.
- **Type system is coherent.** At 390px: `p` and `li` are both Source Serif 4 Variable 17px / 400 / 28.9px — the mid-prose face switch from course one is gone. `h1`, `h2`, `h3` and `.starlight-aside__title` are all Crimson Pro Variable 700. Inline code and code blocks are JetBrains Mono Variable at 13px and 14px.
- **Grids reflow cleanly and rows are even.** Landing `.tmx-grid`: 1 column at 390 (heights 300.9 each at 1440), 2 columns at 768 (277.7 / 277.7 / 275.8 / 275.8 — even within each row), 4 columns at 1440 (all 300.9). `.tmx-panels`: 3 x 237.2 at 1440. No ragged card in any row.
- **Theme toggle is reachable at 390px on both page types** — inline in the header on the splash landing page (no hamburger, since there is no sidebar), and at 40 x 40 inside the mobile menu on lesson pages. The course-one failure where no theme control existed at phone width has not recurred.
- **Tables sit on an opaque `--bg-surface` card with a header row and a hairline frame**, so the scatter field's monospace shell fragments never surface between monospace table cells. Verified in Parchment on `bridge/api-setup/`, which was the exact failure mode in course one.
- **Sidebar active state is legible**: the current page renders a soft brass pill with a 2px brass left rail and full-strength ink, in both themes.
- **The `Interactive` / `Careful` / `Finish` / `Local` sidebar badges render in JetBrains Mono on brass**, not Starlight's stock navy and purple.

## What I did not get to

Stated plainly, so nobody assumes coverage that does not exist.

- **Whether M1 survives a production build.** The brief said use the running dev server and do not build, so every island measurement is a dev-server measurement. `client:only` hydration differs under `astro build`, and `_jsxDEV` is a *dev*-runtime symbol — the production build may well be fine. This must be checked before M1 is triaged as Critical rather than as a broken local install. The control against the beginner dev server rules out the machine and the React version; it does not rule out the build.
- **Real touch-device rendering.** Everything here was measured in desktop Chrome at `devicePixelRatio: 1.5` with a classic 15px scrollbar, in an iframe sized to a true 390px layout viewport. `@media (hover: none)` did not apply, so the copy button's at-rest opacity on an actual phone was inferred from the `pointer: coarse` rule rather than observed. Font smoothing, momentum scrolling, the Android URL-bar height change, and whether the horizontal scroll cue on code blocks and tables is discoverable by touch are all unverified.
- **Six routes were only partially walked.** `bridge/reading-the-device/`, `bridge/talking-back/`, `automation/shell-scripts/`, `serving/local-server/`, `progress/` and `reference/troubleshooting/` were measured for overflow, code-block geometry, island state and page length, but were not visually walked screen-by-screen in both themes. `bridge/reading-the-device/` in particular is the longest page in the course (22,142px tall at 390px, 34 code blocks, 6 tables) and deserves its own pass.
- **Interactive states.** Because no island hydrates, nothing stateful could be exercised: no "Mark complete" click, no progress ring, no avatar picker, no LiveSandbox boot, no lesson-completion styling. If M1 is fixed, all of that is unaudited and should be re-run.
- **Search modal, 404 page, print styles, `prefers-reduced-motion`, RTL, and forced-colors mode** were not opened at all.
- **Renderer instability during the session.** Chrome's remote-evaluation channel timed out several times after scrolling pages in the harness, twice requiring a fresh tab. I could not attribute this to the site — it did not reproduce on demand and screenshots recovered afterwards — so it is recorded here as unexplained rather than reported as a finding. If a scroll-triggered freeze is ever seen on a real device, this note is the first data point.
